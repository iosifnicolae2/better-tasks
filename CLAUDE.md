# better-tasks: project rules
Project rules for working on the better-tasks plugin. Open before shipping a change.

- **Instructions state principles, briefly:** any instruction better-tasks writes (lead and teammate rules, skills, status checks, templates) says only the principle, in a line or two; no step-by-step detail the model can work out itself.
- **Releases:** after shipped changes are pushed to main, cut a release: `scripts/release.sh v<next>`. It pins the marketplace entry to the new tag in a "Release v<next>" commit, tags the plugin package (that commit without the task board, `DEV_ONLY` in release.sh, a child of it off main), pushes, and creates the GitHub release (notes from the commits since the last tag; pass a notes file as the second argument to write them yourself). With `releaseVideos` on (the default), the notes open with a video of the release's tasks, each before and after; it takes a few minutes and the Kokoro voice. `scripts/release.sh --dry-run v<next>` makes the notes and the video and publishes nothing. For an approval question, `scripts/release.sh --draft v<next>` makes them into a draft release to link (its URL printed last), which the release later publishes.
- **Installs get releases, not main:** `.claude-plugin/marketplace.json` points at the latest tag (`github` source `ref` and entry `version`; only release.sh edits them). A push to main reaches users with the next release; .claude/tasks never does. A directory submission tracks the tag, not main.
- **No `version` in plugin.json:** it would win over the entry's `version` and freeze updates.
- **Users who want better-tasks changed:** fork, change, linked install, then ask about a PR upstream (Yes / Not now / Never, saved per user). The rules the lead gets: `.claude/better-tasks/contribute.md`.
